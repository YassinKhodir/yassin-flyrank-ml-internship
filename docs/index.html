Which content pages should be reviewed first?

A simple refresh-opportunity ranking study using a mid-panel month of pseudonymized search data.

Abstract

Which established pages should a content editor review first when review capacity is limited? I studied the March 2026 partition of the FlyRank internship warehouse, using March 1–15 signals and a March 16–31 decline outcome. A fixed rule was compared with a five-feature logistic regression on clients excluded from training. On that held-out group, model precision@100 measured 0.310, compared with 0.150 for the fixed rule and a 0.233 outcome base rate; overall ROC-AUC was only 0.510. The result supports a small human-reviewed priority queue, not automatic content changes or a claim that refreshing causes recovery.

Introduction / Problem statement

An editor may have thousands of pages but time to inspect only a small batch. The decision is not “which pages must be refreshed?” It is “which pages deserve attention first?” A wrong high-priority recommendation wastes review time, while a missed page can leave a meaningful opportunity unnoticed.

The output is a ranked page queue with a score, reason code, and suggested review action. A human checks search intent, business value, content quality, seasonality, cannibalization, technical issues, and editing cost before choosing any action.

Data

The source is the pseudonymized FlyRank ML Internship warehouse release. The full daily-performance table contains about 78.8 million rows; this study used its March 2026 partition, which contains 9,841,378 daily rows. The page-level frame contains 77,400 eligible records from 38 represented clients.

Features use March 1–15 only. The observed label uses March 16–31 and equals 1 when average daily impressions fall by more than 20% from the early window. Pages need at least 100 early impressions, an available GSC flag, and an observed later-window row.

I excluded later-window values, product flags, client and content IDs as features, GA4 fields with uneven coverage, raw queries, domains, URLs, and all identifying fields. The IDs are used only to group and split rows.

Methodology

The five features are early log impressions, CTR, active days, average position, and position volatility. The fixed baseline assigns points for search volume and positions 4–50, with the most position points going to positions 21–50. The learned model is logistic regression with median imputation and standardization.

The final validation holds out entire clients: 28 clients for training and 10 for testing, using seed 42. This tests transfer to a client not seen during fitting. A random page split produced ROC-AUC 0.594, but the grouped split produced 0.510, showing that randomly mixed pages made the model look stronger.

The leakage audit draws a strict timeline: early features, decision moment, later label. Adding a deliberate copy of the label produced ROC-AUC 1.000; that column was deleted. No label-derived, future-window, product-decision, or ID field remains in the model.

CTR had the largest standardized coefficient, followed by average position. The model also produced confident false negatives, especially among pages with strong CTR and good positions. That is a reminder that short-window search behavior, client context, and seasonality are not fully represented by these five fields.

Limitations & honest framing

  • One mid-panel month is not every season or client portfolio.
  • Only 10 clients appear in the held-out evaluation.
  • The eligible population requires observations in both halves of March, which can favor consistently tracked pages.
  • The later-decline label measures movement, not the value of a refresh.
  • No controlled intervention was run, so the analysis cannot claim that refreshing causes recovery.
  • Precision@10 is based on only ten rows and should not be treated as a stable headline.

The safe claim is narrow: on one held-out-client split, the learned score ordered the first 100 rows better than the fixed rule, while overall discrimination was weak.

Ranked recommendations

  1. Review high-priority rows first. Check demand, intent, quality, cannibalization, technical status, and business value.
  2. Use the reason code as a starting question. Low CTR suggests a title/snippet/intent check; positions 21–50 suggest a depth and internal-link review; unstable positions suggest waiting.
  3. Estimate cost before rewriting. A large edit needs stronger evidence than a short diagnostic review.
  4. Monitor the queue. Pause if precision@100 falls below the outcome base rate twice, feature missingness exceeds 10%, or editor rejection exceeds 50% for two batches.
Never automate from this score: publishing, deleting, merging, redirecting, metadata changes, recrawl requests, or claims of expected ranking lift.
